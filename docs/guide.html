快速开始、GitHub Pages 发布手册与常见问题

本页是 首页 的操作补充：如何在本机跑起来、如何把站点发布到 GitHub Pages、 分支模型怎么用、以及站点本身如何维护。所有命令均可直接复制执行。

Step 01

快速开始

仓库零依赖：不需要 npm install，只用 Node.js 内置模块即可完成测试、启动与本地预览。

终端
$ git clone git@github.com:wangruchao-github/aiworker-demo-app.git
$ cd aiworker-demo-app
$ node -v                 # 建议 Node.js 18+
$ npm test                # 单元测试 + 站点约束测试
$ npm start               # 打印 getAppStatus() 运行状态

npm test

运行 src/test.js 单元测试，并串联 src/pages.test.js 站点约束断言。

npm start

启动应用入口 src/app.js，输出运行状态 JSON，便于确认工程可运行。

npm run pages:serve

本机静态服务器，默认 http://localhost:5173，根目录为 docs/。

本地预览文档站
$ npm run pages:serve
▸ 文档站已启动：http://localhost:5173
▸ 静态根目录：docs/

$ npm run pages:build
✓ 已生成 index.html（来源：docs/index.html）

$ npm run pages:check
✓ 根 index.html 与 docs/index.html 已同步
Step 02

分支模型与提交规范

分支模型由 AIWorker 平台统一约定，人工参与改动时请沿用同一套命名。

分支命名规则基线用途
mainmain—仓库初始主干
release/v1.0.0release/{version}main版本分支，所有需求分支的共同基线与汇入点
feat/v1.0.0-DEMO-REQ-105feat/{version}-{reqCode}release/v1.0.0单需求原子改动分支
  1. 从版本分支切需求分支

    git switch -c feat/v1.0.0-DEMO-REQ-105 release/v1.0.0；不要直接基于 main 开发。

  2. 提交信息带署名与需求号

    格式形如 feat(DEMO-REQ-105): 写一个静态页面介绍这个项目，使其可以通过gitub pages 访问 @author wangrc。

  3. 验收后 --no-ff 合并回版本分支

    git merge --no-ff feat/v1.0.0-DEMO-REQ-105，保留需求级 Commit 拓扑，便于审计。

  4. 推送并等待 CI

    推送 release/* 或 main 后，GitHub Actions 自动发布 GitHub Pages。

提示：本仓库的 package.json 中 scripts 仅使用 Node.js 内置能力， 新增脚本请继续遵循「零依赖」原则，避免把构建链引入演示工程。
Step 03

GitHub Pages 发布手册

本需求已确认采用模式 A（GitHub Actions 自动发布，Pages Source = GitHub Actions）， 同时保留模式 B（Deploy from a branch → /docs）作为零 CI 兜底。

模式 A · GitHub Actions 自动发布（推荐，已采用）

  1. 确认工作流文件存在

    仓库根 .github/workflows/pages.yml，推送到 main 或 release/** 时自动执行，并保留 workflow_dispatch 手动重发。

  2. 在仓库设置中切换发布源

    Settings → Pages → Build and deployment → Source 选择 GitHub Actions。

  3. 首次发布

    保存后 Actions 面板会出现 Deploy static content to Pages 任务；绿色即代表 https://wangruchao-github.github.io/aiworker-demo-app/ 已可访问。

  4. 后续更新

    推送即发布，通常 30～90 秒生效；如遇缓存问题，可在 Actions 中手动重跑一次工作流。

模式 B · Deploy from a branch（零 CI 兜底）

  1. 切换发布源

    Settings → Pages → Source 选择 Deploy from a branch。

  2. 选择分支与目录

    Branch 选择 main（或 release/v1.0.0），Folder 选择 /docs。

  3. 保存等待

    约 1 分钟后生效；由于不走 CI，缓存与构建日志需在 Pages 设置页查看。

子路径适配检查清单

项目级 Pages 位于 /aiworker-demo-app/ 子路径下，因此：站内链接一律相对路径； 不使用 / 开头绝对路径；不做 SPA history 路由（深链会 404）；保留 docs/.nojekyll。

回滚方式

优先回滚分支：把 release/v1.0.0 或 main 复位到上一个稳定 commit 并推送，工作流会自动重新发布； 紧急情况下可在 Actions 中对失败任务用同一 commit 重新部署。

常见问题：若访问 404，先确认 Pages Source 已设为 GitHub Actions 且工作流运行成功； 若样式丢失，检查链接是否写成了绝对路径；若资源被吞，确认 docs/.nojekyll 存在。
Step 04

站点维护约定

站点只有一个 canonical 源：docs/index.html。其余文件按下列规则维护。

文件作用维护方式
docs/index.html首页（canonical 源）直接编辑；改完必须执行 npm run pages:build
docs/guide.html本子页直接编辑，样式与脚本内联，无外部依赖
index.html（仓库根）单文件版，可直接双击打开禁止手改，由 scripts/build-pages.mjs 生成
docs/404.html自定义 404 页保持链接为相对路径
.github/workflows/pages.ymlPages 自动发布改动后需在 Actions 中验证一次
修改站点文案的完整流程
$ vim docs/index.html          # 1) 改 canonical 源
$ npm run pages:build          # 2) 同步生成仓库根单文件版
$ npm run pages:check          # 3) 确认同步（CI 与 npm test 也会校验）
$ npm test                     # 4) 跑单元测试 + 站点约束测试
$ git add -A && git commit -m 'docs: 更新站点文案 @author wangrc'
Step 05

FAQ

关于这个站点与它背后的平台，最常被问到的几个问题。

为什么不使用 React / Vite / Tailwind？
本仓库是演示 AIWorker 流程的最小工程，定位是零依赖、零构建。 引入构建链会让「克隆即跑」的演示属性变差，也会让 Pages 发布多一层不确定性。纯 HTML + CSS + 原生 JS 已足够支撑多页文档站。
为什么不做成单页应用（SPA）？
GitHub Pages 与平台内置静态服务都没有 history fallback，/foo 这类深链会真实 404。 因此站点采用「多页 + 相对锚点」结构：首页与子页之间用相对链接，页内跳转用锚点。
根目录的 index.html 和 docs/index.html 有什么区别？
内容一致。canonical 源是 docs/index.html；仓库根的 index.html 由 scripts/build-pages.mjs 生成，作用是让人直接双击根目录文件也能看到完整页面（无需起服务）。 npm run pages:check 会校验两者是否同步，避免两份内容漂移。
站点依赖外部 CDN 吗？离线能看吗？
不依赖。字体走系统字体栈，图标全部是内联 SVG，CSS 与 JS 全部内联在 HTML 中。 因此离线双击 index.html 也能完整渲染。
这个页面本身属于哪个需求？
DEMO-REQ-105「写一个静态页面介绍这个项目，使其可以通过 gitub pages 访问」， 目标分支 feat/v1.0.0-DEMO-REQ-105，基线 release/v1.0.0。 仓库中另有一个需求 DEMO-REQ-101（健康检查与版本信息接口），两者可在 src/ 下对照查看。
