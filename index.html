Branching · 分支策略

三层分支模型：主干、版本、需求

分支模型由平台强制约定，任何一次改动都能在 30 秒内定位到它属于哪个版本、哪个需求。

版本流 需求流 可选回合并
分支命名规则基线职责
main main — 仓库初始主干，承载最小可运行工程
release/v1.0.0 release/{version} main 版本分支：所有需求分支的共同基线，验收后的汇入点
feat/v1.0.0-DEMO-REQ-105 feat/{version}-{reqCode} release/v1.0.0 需求分支：单需求原子改动，携带完整 Commit 记录
约定：需求分支一律从版本分支切出，不直接基于 main 开发； 合并回版本分支使用 --no-ff，保留需求级 Commit 拓扑，便于审计「哪个需求改了什么」。

Publishing · 站点发布

两条发布路径，一条主线路

本需求已确认采用「模式 A」：新增 .github/workflows/pages.yml，Pages Source 设为 GitHub Actions；推送即发布，并保留手动重发能力。

已采用

模式 A · GitHub Actions 自动发布

工作流监听 main 与 release/** 推送，静态发布 docs/，并支持手动重发。

  1. 仓库 Settings → Pages
  2. Source 选择 GitHub Actions
  3. 推送到 main 或 release/** 即自动发布
  4. Actions 页可 workflow_dispatch 手动重跑

模式 B · Deploy from a branch

零 CI 兜底方案：直接由 GitHub 读取分支目录发布，无需任何工作流。

  1. Source 选择 Deploy from a branch
  2. Branch 选择 main（或 release/v1.0.0）
  3. Folder 选择 /docs
  4. 保存后约 1 分钟生效

子路径适配要点

项目级 Pages 走子路径 /aiworker-demo-app/，站点内所有链接必须是相对路径。

  1. 不使用 / 开头的绝对路径
  2. 不使用 SPA history 路由（深链会真 404）
  3. 多页结构 + 锚点跳转，避免依赖前端路由
  4. docs/.nojekyll 防止 Jekyll 吞掉下划线资源
零外部依赖：本站不引用任何 CDN 字体或第三方脚本，CSS 与 JS 全部内联在 HTML 中， 因此在离线环境、弱网环境以及 GitHub Pages 的子路径下都能完整渲染；图标一律使用内联 SVG，不引入二进制资源。
